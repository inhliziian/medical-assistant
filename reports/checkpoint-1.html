Schema

Eight top-level fields, three enums, two nested lists. Source of truth is src/medassist/schema.py; the JSON Schema sent to both providers is derived from it with additionalProperties: false on every object, so both models are constrained by the identical definition.

fieldtyperule
patient_ageint | nullnull if not stated, never guessed

report_typeenum consult / progress_note / discharge / referral / lab / radiologydocument kind

lab_valueslist[{name, value, unit | null}]numeric analytes only; decimal comma → point
medicationslist[{name, dose | null, frequency enum | null}]frequency normalised to 1x/day … as needed
urgencyenum routine / soon / urgentsame day = urgent, days to 2 weeks = soon
follow_up_requiredboolany named follow-up action

Models and configurations

Both providers implement one interface, Provider.extract(instructions, text), with retry, timeout, schema validation and cost accounting in the shared base class. Haiku 5.5 rejects non-default temperature and top_p, so its sampling dimension is the effort level; the local model exposes temperature and top_p. Switching models or settings is a config name in config/runs.toml.

5. Notes and limitations

  • Golden labels were corrected during the first comparison. Two documents had the patient's sex labelled from the seed although the text never states it; the only pronouns referred to relatives. The labels now say unknown and the convention is recorded. Disagreements between model and label are read in both directions: sometimes the label is wrong.
  • Local model size was dictated by hardware. Qwen3 8B on an 8 GB Mac placed only 76% of its weights on the GPU, swapped heavily and timed out after 8 minutes on one document. Qwen3 4B fits entirely and answers in seconds. Model choice for a local deployment is a memory question before it is a quality question.
  • Sampling knobs differ by provider. Haiku 5.5 returns an error for non-default temperature and top_p; thinking depth is controlled by effort. The comparison therefore varies effort on the hosted side and temperature/top_p on the local side.
  • Token counts are not comparable across providers. The two APIs tokenize differently and deliver the schema differently. Within one provider they are, which is what the cost column needs.
  • Generation bias. The documents were written by Claude Opus 5.5, the same family as the hosted model. The deterministic noise pass and the planned addition of real-world texts (see docs/hf-unstructured-data-research.md) mitigate but do not remove this.
  • Ten golden items means one field is 1.25 percentage points. Differences of a few points between runs are not significant; the field-level table is more informative than the headline number.

6. Questions for the Q&A

Each question is tied to a measurement on this page, so the discussion can start from evidence rather than opinion.

Q1. Grammatical gender as evidence: how far may the model infer?

What we observed. Document 037 is a Ukrainian consult note. The only gender cue is the masculine noun «Пацієнт», five times; there is no pronoun, no title, no gendered verb form. Haiku 5.5 at low effort answered unknown (sex accuracy 90.0%), at high effort male (100.0%). Our golden label says male, and prompt v2 states the rule explicitly, after which both models answer male.

Question. Is grammatical gender acceptable evidence for a labelled field, or does it violate the "never guess" principle we apply to age? Where do practitioners draw the line between inference from language and invention? Should the labelling convention be the schema's job (a field description) or the prompt's?

Q2. Temperature changed nothing for the local model. Is that expected under constrained decoding?

What we observed. Qwen3 4B scored 68.8% at t=0 and 68.8% at t=0.7, with an identical per-field profile in both runs, over 50 documents. Ollama constrains generation to the JSON schema, so the sampler can only choose among tokens that keep the output valid.

Question. With schema-constrained decoding, is a temperature / top_p comparison still a meaningful experiment for extraction tasks? If not, which knob should take its place as the second "sampling" dimension: thinking on/off, context length, quantisation, model size? And for hosted models that reject temperature (Haiku 5.5), is effort the right analogue?

Q3. If sampling does not move accuracy, the prompt is the only lever left. How much belongs in the prompt versus the schema?

What we observed. Prompt v2 adds conventions learned from v1 errors (bare diagnosis names, sex from the patient's own pronouns, no invented units, dose and frequency in their own fields). On the golden set it lifted Haiku from 88.8% to 97.5% and Qwen from 68.8% to 83.8%. Some of these rules could instead live in the schema, for example a stricter enum for frequency or richer field descriptions.

Question. What is the recommended split between prompt rules and schema design? Do field descriptions in a JSON Schema reach the model as reliably as prompt text for both hosted and local providers? Is there a point where a long rule list starts to hurt a small local model?

Q4. AI-generated data evaluated by AI: how serious is the familiarity bias, and how should we control for it?

What we observed. The 50 documents were written by Claude Opus 5.5 agents from deterministic seeds, then dirtied by a script. The hosted evaluated model is Claude Haiku 5.5, a different model but the same family; the local model is Qwen3 4B, a different family. Risk: Haiku reads Opus-written text more comfortably than it would read real clinic notes, inflating its score relative to Qwen.

Question. Is a different model within the same family enough separation for a course project, or should generation and evaluation come from different vendors? How would you measure the bias in practice, for example by adding 10 real notes (mtsamples, ACI-Bench transcripts) and checking whether the Haiku-versus-Qwen gap changes? Is documenting the bias in the limitations section sufficient at this stage?

Q5. Ten golden items: how much variance is acceptable before a difference counts?

What we observed. The same Haiku low-effort configuration scored 88.8% on one run and 91.2% on another with identical prompt and settings. With 10 golden documents, one field equals 1.25 percentage points, so differences of 2 to 3 points are within noise.

Question. What golden-set size do you consider the minimum for a trustworthy model comparison in a project like this? Should we report confidence intervals, repeat runs, or simply grow the set as we find errors in production, as the regression-suite approach suggests?
